# 实现后 A/B 验收与收敛规则

确认日期：2026-10-02。状态：计划，尚未运行 A/B。

用户要求：收益有待验证的增强可以先实现，但实现后必须在当前案例上看到收益，才算收敛。`explain_signal_driver` / NPI 返回增强属于这一类。确定性采样与 Source Graph 修复不需要模型 A/B；它们的功能、回归、资源验证仍按 [PLAN.md](PLAN.md) 执行。

## 1. 实验边界

| 实验 | A | B | 必须回答的问题 |
| --- | --- | --- | --- |
| E1，必做 | 已验收的 P0 底座 + 原有 NPI/driver 输出 | 同一底座 + NPI/explain_signal_driver 的可采样依赖、角色和按需输出 | 多出的结构化信息是否实际改善调试任务，而不是只增大上下文？ |
| E2，仅在实现组合工具时做 | 已收敛的 E1 | E1 + 薄组合工具 | 合并调用在已有依赖包之外是否还有收益？ |

“实现”与“收敛”分开：原型可以先写、可以由测试启用；未完成 A/B 或没有收益时，只能记为已实现待验证/待优化，不能因单测通过认定完成。默认查询仍不自动展开依赖。

P0 修复导致的成功查询不归功于 E1。A/B 两边都必须包含相同的 P0 修复。NPI 路径/返回格式、额外依赖、采样建议若一并改变，先测整体；要认定其中某个独立改动的收益，必须补相应消融，不能把整体收益归给尚未分离测试的字段。同一个依赖功能在 NPI 与 Source Graph 上的实现不必人为拆开，但必须分别报告后端结果。

## 2. 固定当前案例与任务

依据 [cases.json](cases.json) 和 [README.md](README.md)。下面是评审者的任务/验收映射，不直接作为被测 agent 的答案提示。

| 案例 | 任务 | 必要证据 / 防止的误判 | E1 用途 |
| --- | --- | --- | --- |
| C1 OpenTitan UART | 解释 tx_q 与 tick 的边沿关系，核对数据与控制输入 | 正确区分 pre-edge 条件与 post-edge 状态；不把正常更新归为错误 | 主要收益案例：真实 NPI 的依赖返回 |
| C2 X1 数据比较错误 | 从症状追查数据在哪个已检查边界变化 | 上下游取值、实际传输时刻与源码关系；不把 software_exit 当错误写入时刻 | 数据驱动回溯及路径可用性 |
| C3 X1 FSM 完成 | 验证 RUNNING→READY 时 done 的前后相位 | pre-edge done 与 post-edge done 分开；不误判 FSM | 控制条件及正常反例 |
| C4 X2 超时 | 区分状态逻辑与未满足的外部条件 | 检查响应路径两侧；不只看到 RUNNING 就改状态机 | 主要收益案例：控制依赖与继续回溯 |
| C5 X3 正常对照 | 检查所选映射与转移是否有同类异常 | 使用本运行事实，不能靠“对照”标签判正常；局部结论不外推全局 | 防止返回更多候选导致误归因 |

至少覆盖这五个案例，不以合成单测替代真实产物复测。C1/C4 是预先指定的 E1 受益观察点；C1/C3/C5 的正常行为是必须保留的反例。NPI 与 Source Graph 的结果分开列，不能只展示其中较好的后端。

另做一个小任务：仅要求定位 C1 的驱动源码，不要求继续分析。用于确认默认依赖关闭时不会强行多查信号；它不替代五个完整案例。

### 被测输入与 oracle 分离

实现/评审会话可以阅读全部研究材料；被测 agent 必须是新上下文，只得到路径、症状、允许的查询范围和同一 debug discipline。

- 不把研究报告、历史分析结论、expected_points、patch、提示词中的答案或之前 A/B transcript 提供给被测 agent。
- 不在已经知道结论的实现会话里“分别扮演 A 和 B”。
- 两边任务提示一致，不能只告诉 B “请使用新依赖选项”或暗示哪条链更可疑。新工具自己的参数说明允许作为真实产品差异，但要保存并计入输入成本。
- 原始 RTL 存在 mutant 注释，因此原样本实验不是严格盲测。两边保留相同源码可见性、记录提示泄漏限制；每个根因结论仍必须有本运行的双侧波形证据。不能仅凭读到注释计为成功。
- 如另建去提示副本，单独标识，不能让一组看原版另一组看修改版，也不能因此替代原案例的结果。

## 3. 版本、会话与环境控制

1. 先完成 P0 功能验收，记录代码 SHA/未提交 diff 摘要，冻结 E1-A 基线。不要用会重置用户工作区的操作切换版本；可以用隔离 checkout/worktree 或明确的实验开关。
2. 确认每个评测 MCP 服务实际加载对应版本的 server/worker，记录启动入口与版本指纹。仅编辑工作区而服务仍跑旧代码不算新版本测试。
3. 默认模型固定为 `gpt-6-astra`，reasoning effort 固定 `max`；两组同一可用模型版本/服务模式。此设置沿用用户当前条件，不是模型深度对比实验。
4. 每个 run 使用干净模型上下文和独立 MCP 会话；按正常 discovery/hierarchy/scan 流程获得新 handle。跨运行比较要在最后一次 discovery 后建立双方上下文。旧 handle/cursor 不作为输入复用。
5. 使用同一份只读波形/源码/日志，核对 manifest 和来源限制。实际完整历史编译版本仍不能独立证明时，两边如实记录同一限制。
6. 采用顺序评测，避免 FSDB/NPI 锁、worker admission 或 license 竞争污染时间数据。统一服务冷热条件；推荐主实验均为新 MCP 进程，OS 文件缓存无法完全控制时记录并交替 A/B 顺序。额外热缓存实验单独报告。
7. 固定工具权限、非目标工具 schema、调试纪律、任务预算和重试规则。总输入/输出 token、工具调用数及 wall-time 上限在正式 run 前记录；不在 B 失败后单独增加预算。
8. 如果 token usage 无法取得，明确标缺失。字节数不能冒充 token。可以在正式运行前选择时延为效率主指标，但不能看完结果后挑好看的指标。

不要求本轮新建 RTL 缺陷、重新跑仿真或生成额外 KDB；优先使用已有产物和可用 KDB。真实 NPI 前提不满足时，该案例标为未完成，而不是以 Static/Source Graph 结果替代 NPI 验收。

## 4. 建议规模与重复规则

用户要求的是实现后在现有案例上证明收益，没有指定调用额度。以下是建议的工程起始规模；新 session 在正式实验前评估运行成本并记录采用的规模。若调整，必须在看结果之前说明原因和重复性判据；不能降为展示一次成功。

- 每个案例、每个 arm 至少 3 次，形成 3 个 A/B 配对；五个案例即 E1 最少 30 个独立 run。
- 同一配对保持模型、任务预算和环境一致；按 AB、BA、AB 或事先固定的交替次序执行。
- 3 次是本轮工程验收起点，不是统计显著性的保证。结果接近噪声或方向不稳定时，增加配对或明确“不足以认定收益”。
- 保留失败、超时和未使用新字段的 run。软件预算超时属于结果；外部基础设施失败可以标无效并重跑完整配对，但必须保留原始记录和无效理由。
- 小幅提示调优/输出调整后重新冻结版本和对照；不能删除旧失败记录，只报告最佳一次。
- 不具备独立运行入口、模型额度或可核验 usage 时，列出缺项，状态保留“已实现待 A/B”。固定工具脚本回放只证明功能/性能，不能代替 agent A/B。

## 5. 指标

### 正确性先于成本

逐 run 检查：

- 值、路径、bit selection、clock 和采样相位是否正确。
- 是否检查了至少两个竞争解释需要的证据，而非照着返回候选宣称根因。
- 是否定位异常发生的边界，是否区分传播点与起点。
- 是否保留 backend、coverage、未 dump、未检查范围和历史来源限制。
- C1/C3/C5 是否出现新的正常行为误判。

“成功”是完成该任务的必要证据和正确解释；不是提到了预期文件名。评分 oracle 按 cases.json 的事实建立，但允许另一条同样充分、可核验的取证路径。

### 效率与选择负担

记录：

- 整个任务模型 input/output token；能取到时单列 cached input、reasoning token，避免和总 output 重复相加。
- 工具描述、MCP 返回、源码读入等输入构成；新增 JSON 字节单列，不能仅看一个响应的长度。
- 总 elapsed、有效/无效调用、失败恢复、源码读取与名称搜索次数。
- 返回依赖数、实际用于相关取值/条件验证的依赖数、无关信号读取、错误路径请求。
- 后端查询/波形读取耗时、事件量、可获得的 RSS 与取消/超时表现。

“后续未引用”只是观察指标，不等于模型没读；“采样过”也不等于对推理有帮助。最终以证据正确性与任务总成本判断。

## 6. 收敛门槛

下列数值是本轮建议的工程门槛，不是已经测出的提升。可以在正式运行前根据计量能力/噪声作一次有记录的修订；禁止看到结果后降低门槛。

### 所有增强都必须满足

- 对应功能/契约/并发/取消回归通过。
- 每个当前案例都有有效 A/B 数据；B 成功次数不低于 A。
- 没有新增的路径、相位、覆盖或正常反例误判；新增错误必须修复后复测。
- 按需依赖默认关闭，简单定位任务不被自动升级成大范围取证。
- 下列质量或效率收益至少一项成立，且与新增实现有可解释关系。

分别记录 NPI 返回增强与通用 driver 依赖包的收敛状态。宣称 NPI 增强有收益，必须有 C1 的真实 NPI 受益证据，不能用 C4 的 Source Graph 收益代替；通用 `explain_signal_driver` 工作流可由 C1 或 C4 等适用案例证明。若只证明一部分，另一部分继续待验证/待优化。捆绑开关只支持对整套工作流的结论，独立字段的归因遵守第 1 节消融规则。

### 可接受的收益

**质量路径：** 在至少一个当前目标案例上，B 在同预算下完成了 A 未完成的必要证据/正确结论，至少 2/3 配对重复出现；其他案例无退化。允许在预先固定的预算内付出更多 token，但必须明确收益属于质量，不声称省 token。

**效率路径：** 在双方都成功的配对上，至少一个预登记主要受益案例的任务总 token 中位数下降 ≥10%，且至少 2/3 配对方向一致；五案例合计 token 不上升，整体 elapsed 中位数不明显恶化（默认容忍 10% 以内噪声）。若正式运行前改选 elapsed 为主指标，则采用 ≥10% 的同类标准，并报告 token 是否可测及其变化。缺少 token 数据时不能得出省 token 结论。

调用次数更少、返回更漂亮、一个正确的 JSON 或一次幸运定位都不能单独满足收益条件。默认值是否适合所有任务也不能仅从开启依赖的受益案例外推。

### 没有收益时

保留 P0 已通过的修复，记录 E1/E2 的负结果，缩减字段/展开范围或重做适配，再做新的配对测试。也可以暂留实验开关关闭；状态为“待优化”，不是“已收敛”。不要求为了证明方案正确而无限试验或挑选案例。

## 7. 交付文件

在本目录新建 `evaluation/<experiment-id>/` 保存：

- `manifest.json`：双方版本、feature flags、模型/effort、任务提示与工具 schema 指纹、预算、冷热条件、artifact 指纹、运行顺序、冻结的判据。
- `runs.jsonl`：每个 run 的 case/arm/repeat、状态、实际 usage、elapsed、调用/依赖使用指标、失败原因、原始 transcript 路径。
- `grading.jsonl`：逐案例证据评分与可点击的事实引用。
- `REPORT.md`：逐案例与汇总 A/B 表、正常反例、代价/限制，以及“已收敛 / 待优化 / 未完成”的结论。

保存执行命令或 runner 入口；不得把未来要跑的命令写成已执行。用结果更新 [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md)。当前目录受仓库已有 Git 忽略规则影响，需保留本地文件；是否提交由后续用户指令决定。
